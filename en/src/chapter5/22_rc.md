# `Rc<T>`

## Goal of This Episode

Learn to share one piece of data among multiple owners with `Rc<T>`, and understand how reference counting works.

## Concept

Last episode was `Box<T>` — one safe, one key, one owner. But sometimes you need **multiple owners** sharing the same data.

### The Problem: a Value Has Only One Owner

```rust,noplayground
# fn main() {
    let a = Box::new(String::from("hello"));
    let b = a; // Move! a can't be used anymore
# }
```

What if you want both `a` and `b` to use this value?

You might think: "Just `clone` it, right?"

```rust,noplayground
# fn main() {
    let a = Box::new(String::from("hello"));
    let b = a.clone(); // Replicates the entire String's contents
# }
```

That does let both `a` and `b` work. But the catch — the `clone` here truly makes a **complete replica** of the heap data. If the data is large (say a `Vec` holding millions of numbers), every `clone` is a real expense. And `a` and `b` point to **two independent replicas** — changing `a` doesn't affect `b`.

If what you need is "several parties sharing **the same** data," `Box`'s `clone` is the wrong tool.

### `Rc`: Reference Counting

Remember Chapter 4's safe analogy? Rust's default rule is "one safe, one key" — that's ownership. `Rc<T>` breaks that default: it lets you **cut several keys that all open the same safe**.

`Rc<T>` (reference counting) tracks how many keys exist with a "counter":

- Creating the `Rc`: count = 1.
- `.clone()`: count +1 — what you gain is a new key, not a second set of the data.
- An `Rc` leaving scope: count -1.
- Only when the count hits zero is the data truly released.

### `Rc`'s `.clone()` Really Does Just Cut an Extra Key

Remember Chapter 4's definition of `clone`? — **"get a new keychain that works just like the original, while making sure that doing so causes no trouble."** For types like `String` or `Vec<i32>`, the way to "make sure" is to buy a new safe and replicate its entire contents.

`Rc` is the exception Chapter 4 foreshadowed: its `.clone()` **really does just cut an extra key**. You get a new key (a new `Rc` value) pointing at the same safe, and the count goes +1 — the data inside the safe is not replicated at all, which is why it's fast and cheap.

So what does `Rc` rely on to "make sure nothing goes wrong"? Not replicating data, but that counter. That's also why `Rc`'s `Clone` is hand-implemented by the standard library rather than `derive`d — `derive` only knows the "call `clone` on every field" trick.

### `Rc` Is Read-only

`Rc<T>` provides only immutable access — every owner can read, none can modify. If you need modification, `RefCell` comes later.

### Wait — Didn't Chapter 4 Warn Against Copying Keys?

Chapter 4 warned that simply copying a key to the same safe can cause trouble. So how can `Rc` cut several keys safely? Two things to know:

1. **The counter's cost**: `Rc` keeps an internal counter tracking how many keys exist, so it knows when to destroy the safe. That counter must update on every `clone` and `drop` — overhead `Box` doesn't have. `Box` guarantees a single key and destroys at scope exit, no counting needed. `Rc` isn't a primitive operation like `Box`; it buys "multiple owners" with extra machinery.
2. **Usage restrictions**: when we get to multithreading, we'll see that `Rc` in fact can't avoid data races in certain situations, so it comes with usage restrictions. Just know this for now.

Put differently: Rust's native ownership rule is "one owner" — a language-level guarantee at zero cost. `Rc`'s "multiple owners" are **simulated** at runtime with a counter, sidestepping the native restriction, at the price of extra cost and limits.

Also note: `Rc` itself still obeys ordinary ownership rules — each `Rc` variable (each key) is an independent value that moves and `drop`s as usual. The only special thing is the level `.clone()` operates at: cutting an extra key, not buying another safe.

## Example Code

```rust,editable
use std::rc::Rc;

fn main() {
    // Create an Rc; count = 1
    let a = Rc::new(String::from("shared data"));
    println!("Created a, count = {}", Rc::strong_count(&a));

    // clone just cuts an extra key: count +1, no second set of the data
    let b = a.clone();
    println!("Cloned to b, count = {}", Rc::strong_count(&a));

    let c = a.clone();
    println!("Cloned to c, count = {}", Rc::strong_count(&a));

    // a, b, and c can all read
    println!("a = {}", a);
    println!("b = {}", b);
    println!("c = {}", c);

    {
        let d = a.clone();
        println!("Inside the scope, count = {}", Rc::strong_count(&a));
    } // d is dropped; count -1
    println!("After leaving the scope, count = {}", Rc::strong_count(&a));

    // A practical use: several structs sharing one piece of data
    let shared_name = Rc::new(String::from("Rust"));

    let greeting1 = shared_name.clone();
    let greeting2 = shared_name.clone();

    println!("1: {}", greeting1);
    println!("2: {}", greeting2);
}
```

## Recap

- `Rc<T>` uses reference counting to share one piece of data among multiple owners.
- `Rc::new(value)` starts the count at 1.
- `.clone()` really does just cut an extra **key**, without a second set of the data: count +1, very cheap.
- Dropping an `Rc` decrements the count; the data is released at zero.
- `Rc` is **read-only** — every owner may read, none may modify.
- Rust's native "single owner" is a zero-cost language guarantee; `Rc`'s "multiple owners" are simulated at runtime with a counter, carrying extra cost and limits.
- `Rc` itself follows ordinary ownership rules (move, `drop`) — each key is an independent value.
- Check the current reference count with `Rc::strong_count(&x)`.
